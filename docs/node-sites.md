# Сайты Node: установка и замена

Менеджер поставляет семь статических сайтов. Дополнительные контейнеры,
серверная авторизация и процессы Python/Node.js для их работы не нужны.
Nginx раздаёт файлы и выполняет ограниченные запросы к источникам контента.

| ID | Сайт | Источник |
| --- | --- | --- |
| `01-northline` | [Line](northline.md) | Mastodon |
| `02-aster-observatory` | [Aster](aster.md) | Rutube и комплектный снимок каталога |
| `03-morrow-coffee` | [Morrow](morrow.md) | Yappy |
| `04-signal-works` | [Spros](spros.md) | Ответы Mail |
| `05-field-notes` | [Svod](svod.md) | Русская Википедия |
| `06-loop-archive` | [Loop](loop.md) | gifs.ru |
| `07-fokus-news` | [Fokus](fokus.md) | РИА |

Сайты 8–10 больше не поставляются и не доступны для новой установки.
Обновление самого менеджера не удаляет существующий сайт на ноде. Его можно
заменить любым ID из таблицы; архив старого сайта остаётся пригодным для отката.
Идентификаторы сайтов 1–7 сохранены, хотя их названия и содержимое изменились.

## Чистая установка

Следуйте [инструкции установки Node](../README.md#чистая-установка-node),
выбрав `--template <ID>`. Для каждого из семи шаблонов менеджер устанавливает
все файлы сайта, общий каталог `shared`, nginx-прокси и CSP. Aster получает
подготовленный `data/catalog.json`; скачивание каталога при установке не требуется.
Сборка фронтенда не нужна.

`--site-source` предназначен для готового самостоятельного сайта. Копия каталога
встроенного шаблона в произвольном месте не распознаётся по имени: её общие
ресурсы и маршруты оператор готовит сам. Для комплектных сайтов используйте
`--template`.

## Замена существующего сайта

Обновите менеджер. Если установка ещё не принята, либо вы осознанно изменили её
файлы, проверьте изменения и выполните adoption:

```sh
sudo rwm adopt --path /opt/remnanode --role node
sudo rwm --json inventory
sudo rwm disguise list
sudo rwm disguise apply 02-aster-observatory
```

Не выполняйте повторный adoption вслепую: он принимает текущее содержимое как
доверенную исходную конфигурацию. Для уже принятой неизменённой установки
достаточно `disguise apply`. Повторное применение того же ID обновляет файлы и
известные старые маршруты. `rwm update` обновляет компоненты Remnawave, а
`rwm manager update` — менеджер; эти команды сами по себе не заменяют сайт.

Замена поддерживает Node с контейнерным nginx и одним обнаруженным каталогом
сайта. Из нормализованного Compose определяется его bind mount под `/var/www/`.
Менеджер меняет только `server` с соответствующим прямым `root`; другие
виртуальные хосты сохраняются. Обрабатываются все такие серверные блоки,
в том числе отдельный origin CDN. Конфигурация должна быть учтена в inventory
и находиться внутри каталога установки.

Если `root` находится внутри `location`, настройки server вынесены в `include`,
nginx системный, каталогов сайта несколько или подходящий server не обнаружен,
автоматическая замена останавливается до изменения файлов. Подготовьте
однозначную конфигурацию и повторите adoption. Неизвестная CSP и изменённые
вручную маршруты `/_images/`, `/_northline/`, `/_aster/`, `/_morrow/`,
`/_answers/`, `/_svod/`, `/_loop/`, `/_fokus/` также требуют согласования.
Отсутствующая CSP добавляется; известные прежние политики обновляются.
Эти префиксы зарезервированы для сайтов и не должны использоваться для XHTTP.

Перед заменой проверяются хеши сайта и остальных управляемых файлов,
неучтённые файлы, безопасные пути и текущие bind mounts. Создаётся backup,
сайт готовится в соседнем временном каталоге; проверки повторяются перед
переключением. После атомарной замены каталогов проверяется новая конфигурация.
Работающий nginx пересоздаётся с `--no-deps --pull never`, чтобы подключить новые
inode bind mounts. Остановленный nginx пересоздаётся без запуска; проверка
выполняется одноразовым контейнером. При ошибке возвращаются сайт,
изменённые конфигурации и inventory. Проверенный прежний сайт удаляется из
временного каталога только после успеха.

## Дополнительные настройки

| Настройка | Поведение при замене сайта |
| --- | --- |
| XHTTP и Unix-сокеты | Существующие listen, upstream, пути, заголовки и тайм-ауты сохраняются; Config Profile в Panel не меняется. |
| Яндекс/Beeline CDN | Транспортные location и настройки origin сохраняются. Правила внешнего CDN менеджер не редактирует. |
| WARP | Интерфейсы, ключи, routing и конфигурационные файлы не изменяются; команды WARP не вызываются. |
| Subscription Page | Её сервис, env и отдельный nginx server сохраняются; шаблоны применяются только к роли Node. |
| TLS, UFW и секреты | При замене сертификаты, правила firewall, env и SECRET_KEY не меняются. |
| Обновление Node | Выполняется отдельно и не заменяет сайт; см. [сохранение транспортов](xhttp-yandex-preservation.md). |

Пересоздание работающего nginx может кратковременно прервать обслуживаемые им
соединения, включая XHTTP и Subscription Page, если она использует тот же nginx.
Смена сайта не является перезапуском Node или обновлением транспортов.

Если сайт доступен через CDN, запросы к служебным префиксам из предыдущего
раздела должны доходить до этого nginx без переписывания пути и query string.
Для них нельзя включать принудительное кеширование. `/index.html` получает
`Cache-Control: no-cache`; существующий пользовательский location для него
сохраняется и должен обеспечивать повторную проверку HTML. JavaScript и CSS
имеют параметр `v`, зависящий от содержимого всей цепочки модулей. CDN должен
учитывать query string в ключе кеша. При прежних правилах кеширования HTML
потребуется очистка кеша CDN после замены.

Nginx должен разрешать DNS и обращаться по HTTPS к источникам выбранного
сайта. Известные прокси ранее установленных сайтов сохраняются и обновляются;
их источники также могут потребоваться при `nginx -t`. Детали маршрутов,
TLS и кеширования — в [описании прокси](disguise-image-proxy.md).

## Проверка и восстановление

После замены откройте сайт в браузере: проверьте загрузку JS/CSS, ленту,
поиск, изображения и просмотр материала. Затем проверьте используемые
XHTTP/CDN-подключения, Subscription Page и WARP. Локальный `nginx -t`
не проверяет внешнюю доступность CDN или работу клиента через Xray.

```sh
sudo rwm service status
sudo rwm diagnose
sudo rwm backup list
sudo rwm backup verify /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz
sudo rwm backup restore /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz --without-database
```

Восстановление возвращает управляемую конфигурацию из архива; это не только
отмена сайта. Учитывайте изменения, сделанные после создания backup.
Подробнее — [восстановление](rollback-recovery.md).

Профили, сессии и пользовательские материалы находятся в браузере посетителя
и не входят в серверный backup. Замена файлов сайта их не очищает. Доступ к ним
зависит от того же origin и поддержки прежнего формата конкретным приложением;
смена домена или протокола не переносит данные автоматически.

## Проверки в репозитории

Из корня проекта, Python 3.12+:

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_site_deployment.py' -v
PYTHONPATH=src python3 -m unittest discover -s tests -q
```

Первый набор проверяет ресурсы всех семи сайтов, переключения между ними,
замену удалённого шаблона, сохранение остальных настроек и раздачу через
настоящий nginx (если он установлен). Полный набор менеджера рассчитан на
Linux с root-правами; на macOS часть проверок Linux-путей и владельцев файлов
неприменима. Временный каталог для проверок путей не должен проходить через symlink.
Браузерные сценарии и локальные preview описаны в документации каждого сайта.
