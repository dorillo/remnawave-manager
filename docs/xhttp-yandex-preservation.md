# Сохранение XHTTP, Яндекс CDN и Beeline CDN при обновлении Node

Обновление отдельной Node меняет только `image:` её сервиса в существующем Compose и пересоздаёт только этот сервис с `--no-deps`. Nginx, его bind mounts, сайт-заглушка, env-файлы, Unix-сокеты, WARP и конфигурации Яндекс CDN/Beeline CDN не переписываются менеджером. Эта гарантия действует только для объектов, которые были обнаружены и записаны в inventory.

Текущая целевая версия из compatibility manifest — Remnawave Node `3.3.2`. Образ загружается с зафиксированным digest и сверяется после `docker pull`.

## Обязательная инвентаризация

Перед первым обновлением существующей Node выполните:

```console
sudo rwm --json adopt --path /opt/remnanode --role node
sudo rwm --json inventory
```

Проверьте в JSON как минимум поля:

```json
{
  "xhttp_sockets": [
    "/dev/shm/nginx.sock"
  ],
  "warp_interfaces": [
    "warp"
  ],
  "features": {
    "xhttp_stream_separation": true,
    "yandex_cdn": true,
    "beeline_cdn_get": false,
    "beeline_cdn_post": true
  }
}
```

Названия сокетов могут отличаться. `warp_interfaces` нужен только на Node с WARP.

Inventory формируется из нормализованного Compose и обнаруженных nginx-файлов. Для контейнерного nginx менеджер рассматривает существующие исходные файлы bind mounts, направленные в `/etc/nginx/`, а сайт-заглушку — каталоги, направленные в `/var/www/`. Для системного nginx просматриваются файлы из `/etc/nginx/sites-enabled`, содержащие признаки Remnawave или локальных upstream `127.0.0.1:3000/3010`.

Unix-сокет регистрируется в `xhttp_sockets`, если в выбранном nginx-файле есть директива `listen` или `server` с путём под `/dev/shm` либо `/run`, оканчивающимся на `.sock` или `.socket`, либо прямой `proxy_pass http://unix:/...socket;` к такому пути. Флаг `xhttp_stream_separation` также может стать `true` только из-за текста `xhttp`; сам по себе этот флаг не означает, что конкретный сокет записан в список ожидания.

Яндекс CDN определяется эвристически: по слову `yandex` либо по совместному
присутствию признаков `proxy_protocol_addr` и `cdn`.

Beeline определяется отдельно по реально объявленному и используемому Nginx
upstream: `xray_beeline_xhttp` для старой GET-схемы и `beeline_xhttp` для новой
POST-схемы. Результат записывается соответственно в `beeline_cdn_get` или
`beeline_cdn_post`, поэтому Beeline больше не маскируется под `yandex_cdn`.
Учитываются только реальные директивы `upstream` и `proxy_pass`, а не
совпадения в комментариях. Эти флаги сообщают об обнаружении, но не заменяют
внешний тест CDN.

Если нужного nginx-файла или сокета нет в JSON, менеджер не сможет гарантировать его сохранение. Остановитесь до обновления, исправьте bind mounts или расположение конфигурации и повторите `adopt`. Особенно внимательно проверьте:

- bind mount целого каталога nginx вместо отдельных файлов;
- конфигурацию во внешнем include, который не попал в inventory;
- сокет с нестандартным каталогом или окончанием;
- системный nginx-файл без распознаваемых признаков Remnawave;
- конфигурацию Яндекс CDN без распознаваемых маркеров.

После любого осознанного изменения nginx, env, сайта или Compose снова изучите изменения и выполните `adopt`. Иначе `rwm update` остановится из-за расхождения конфигурации. Повторная инвентаризация принимает текущее содержимое как новую доверенную базовую линию, поэтому её нельзя выполнять вслепую после неизвестных изменений.

## Что происходит до переключения образа

Команда обновления:

```console
sudo rwm update
```

До изменения Compose менеджер:

1. требует чистое inventory без изменений управляемых файлов;
2. доказывает, что исходный образ относится к поддерживаемой версии;
3. создаёт и проверяет локальную резервную копию перед обновлением;
4. загружает Node `3.3.2` и сверяет digest;
5. передаёт текущий `SECRET_KEY` новому образу через stdin и проверяет CA, подпись и соответствие ключа без сохранения секрета;
6. получает текущий сгенерированный Xray JSON через Node CLI;
7. проверяет входящие подключения Reality на отсутствие явного `minClientVer`;
8. запускает `rw-core -test` из нового образа с `--network none`, файловой системой только для чтения, без capabilities и только с подключённым для чтения временным JSON.

Если тест нового ядра не проходит, Compose ещё не изменён.

Node `3.3.2` сохраняет требование Reality-клиентов не ниже `26.3.27`, когда `minClientVer` не задан. Менеджер не подставляет `0.0.0`. Только после проверки всех клиентов риск можно принять явно:

```console
sudo rwm update --panel-3-3-ready --accept-reality-client-risk
```

Если исходную версию образа нельзя доказать по известному digest или поддерживаемому тегу, обновление также останавливается. Параметр обхода предназначен только для вручную проверенного исходного образа:

```console
sudo rwm update --panel-3-3-ready --accept-unknown-source
```

Оба подтверждения при необходимости можно совместить. Для неинтерактивного подтверждения самой операции существует `--yes`:

```console
sudo rwm update --panel-3-3-ready --accept-reality-client-risk --accept-unknown-source --yes
```

Эти параметры не исправляют несовместимый Xray JSON и не расширяют набор защищённых файлов.

У `rwm update` нет режима пробного запуска. Новое ядро тестируется до изменения Compose, но после успешных предварительных проверок команда продолжит реальное обновление. `--yes` только пропускает текстовое подтверждение. Отдельно можно проверить текущее состояние и создать дополнительную резервную копию:

```console
sudo rwm diagnose
sudo rwm backup create --reason before-node-update
```

Эти две команды не воспроизводят проверку обновления новым ядром и не гарантируют его успех. Путь созданного архива затем можно передать команде `rwm backup verify`, показанной ниже.

## Что сохраняется во время обновления

Непосредственно перед пересозданием Node менеджер фиксирует:

- SHA-256 всех управляемых файлов, кроме Compose;
- только те зарегистрированные XHTTP-сокеты, которые существуют в этот момент;
- только те зарегистрированные WARP-интерфейсы, которые существуют в этот момент.

Редактор Compose заменяет только прямое поле `image:` сервиса Node и сохраняет остальной текст, комментарии, YAML anchors и стиль перевода строк. Новый Compose предварительно проверяется через `docker compose config -q`.

После `docker compose up -d --no-deps --force-recreate <сервис-node>` менеджер:

- ждёт запуска контейнера;
- проверяет процессы Xray, версию `rw-core` и повторную выдачу сгенерированного Xray JSON;
- ждёт повторного появления ранее существовавших XHTTP-сокетов;
- повторно считает хеши nginx/env/site и других управляемых файлов;
- проверяет, что ранее существовавшие WARP-интерфейсы не пропали;
- только после этого обновляет inventory и фиксирует транзакцию.

Контейнерный nginx не пересоздаётся, потому что запускается только сервис Node
с `--no-deps`. Системный nginx также не останавливается. Таким образом,
существующие TCP Reality, XHTTP TLS через nginx, stream separation, Яндекс CDN
и Beeline CDN сохраняются без генерации новой nginx-конфигурации. Для Beeline
POST защищаются в том числе upstream `beeline_xhttp`, оба XHTTP location,
отключение buffering и увеличенные timeout.

## Автоматический откат

При любой ошибке после создания резервной копии менеджер вызывает восстановление Node без PostgreSQL:

- возвращает Compose и остальные управляемые файлы;
- запускает прежний набор сервисов;
- повторяет проверки работающей Node;
- ждёт сокеты, записанные в сохранённом inventory;
- выполняет `nginx -t` и reload для системного nginx.

Путь к проверенной резервной копии выводится в сообщении. Если автоматический откат также не завершился, менеджер не скрывает исходную ошибку и ошибку отката и оставляет путь к архиву.

Архивы можно проверить и восстановить вручную:

```console
sudo rwm backup list
sudo rwm backup verify /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz
sudo rwm backup restore /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz --without-database
```

Восстановление требует подтверждения вводом `y`; для автоматизации доступен `--yes`:

```console
sudo rwm backup restore \
  /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz \
  --without-database \
  --yes
```

Резервная копия должна принадлежать той же роли, каталогу установки и тем же путям Compose/env, nginx/site и идентификаторам сервисов. WARP-файлы архивируются как дополнительные материалы с `restore: false` и этой командой автоматически не восстанавливаются; обновление Node их не изменяет.

## Проверка после успеха

Проверьте компоненты:

```console
sudo rwm service status
```

На Node с управляемым WARP:

```console
sudo rwm warp status
```

Отдельную проверку `nginx -t` с последующим reload можно выполнить реальной CLI-командой:

```console
sudo rwm certificate reload
```

Затем обязательно выполните внешнюю прикладную проверку каждого используемого транспорта: обычного TCP Reality, XHTTP без CDN, XHTTP через Яндекс CDN и маршрутов через WARP. Такой внешний тест не входит в `rwm update`.

## Границы гарантий

Менеджер гарантирует неизменность и проверяет повторное появление только того, что попало в inventory. Он не гарантирует следующее:

- файлы nginx и include за пределами обнаруженных путей;
- новые файлы, появившиеся после adoption и не записанные в `managed_files`;
- сокеты, не распознанные при adoption или отсутствовавшие непосредственно перед обновлением;
- тип и работоспособность найденного сокета: ожидание проверяет существование пути, а не успешный обмен через него;
- внешнюю доступность Яндекс CDN, корректность его origin, списка разрешённых адресов и PROXY protocol;
- действительность TLS-сертификата и прохождение запроса от CDN до клиента;
- сохранение внешних настроек межсетевого экрана, DNS или CDN, которые не являются управляемыми файлами;
- отсутствие параллельного изменения Config Profile в Panel во время обновления Node;
- резервную копию сгенерированного Xray JSON или самого Config Profile в Panel.

Признаки `yandex_cdn`, `beeline_cdn_get` и `beeline_cdn_post` используются как
результат обнаружения. Для них нет отдельных веток миграции внешнего CDN.
Защита обеспечивается тем, что обнаруженные nginx-файлы остаются байт-в-байт
неизменными, а сервис nginx не пересоздаётся.

Если сокет уже отсутствует до начала обновления, он исключается из ожидания. Если WARP-интерфейс уже отсутствует, он исключается из проверки сохранения. Поэтому исправляйте исходное состояние до запуска обновления, а не рассчитывайте, что команда восстановит ранее сломанный транспорт.
