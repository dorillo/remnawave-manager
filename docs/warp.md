# Встроенное управление WARP

Remnawave Manager устанавливает и обслуживает WARP самостоятельно. Он не скачивает и не запускает сторонние установочные shell-скрипты. На отдельном сервере Node используются системный WireGuard, `wg-quick`, собственные systemd-проверки и зафиксированный бинарный файл `wgcf`.

WARP поддерживается только на сервере с ролью `node`. Совмещённая установка Panel и Node не поддерживается. Перед установкой Node должна быть принята под управление менеджера:

```console
sudo rwm adopt --path /opt/remnanode --role node
```

Менеджер проверяет, что контейнер Node работает с `network_mode: host`. Если в Compose задано `cap_drop: ALL`, контейнеру также должна быть возвращена возможность `NET_RAW`.

## Модель маршрутизации

Менеджер всегда формирует профиль WireGuard с `Table = off`. В нём нет `DNS`, `PreUp`, `PostUp`, `PreDown`, `PostDown`, `SaveConfig` и других командных хуков. Поэтому включение интерфейса `warp` само по себе не заменяет основной маршрут сервера, DNS-резолвер или правила межсетевого экрана.

При установке, ротации и ручных действиях start/stop/restart менеджер сравнивает до и после операции:

- маршруты IPv4 и IPv6;
- policy rules IPv4 и IPv6;
- полный набор правил nftables;
- хеши `/etc/resolv.conf`, `/etc/ufw/user.rules` и `/etc/ufw/user6.rules`.

Если эти данные изменились, операция считается неуспешной. Выборочный IPv4-трафик направляется через WARP не системным маршрутом по умолчанию, а правилом Config Profile с привязкой исходящего подключения к интерфейсу `warp`. Менеджер намеренно задаёт этому outbound стратегию `UseIPv4`: `Table = off` вместе с `SO_BINDTODEVICE` обеспечивает такой маршрут без изменения системной таблицы IPv4, тогда как аналогичный неявный маршрут IPv6 ядром не гарантируется. Системный IPv6 менеджер не перенастраивает.

## Зафиксированный wgcf

Текущий контракт совместимости разрешает только `wgcf 2.2.32`:

| Архитектура | Файл | SHA-256 |
| --- | --- | --- |
| x86_64/amd64 | `wgcf_2.2.32_linux_amd64` | `2ff97f2201972ce582a424455d50a3719a380eef0cd1f3144f7779348e122a2c` |
| aarch64/arm64 | `wgcf_2.2.32_linux_arm64` | `21fe21d9f61db9b381d71200f6f59c7949e0bb455446edcb33dda6ad6a8fcf8f` |

Загрузка разрешена только с доверенных адресов GitHub Releases и проверяется по SHA-256. Подмена версией с тем же именем или передача произвольного локального бинарного файла завершается ошибкой.

Для установки из заранее загруженного файла используйте:

```console
sudo rwm warp install --accept-tos --wgcf-file /root/wgcf_2.2.32_linux_amd64
```

Путь меняется согласно архитектуре сервера. Проверка хеша остаётся обязательной.

## Новая установка

Сначала выполните неизменяющее состояние сканирование:

```console
sudo rwm warp scan
```

Для машинно-читаемого результата глобальный параметр `--json` указывается перед командой:

```console
sudo rwm --json warp scan
```

Если существующая конфигурация или конфликт не обнаружены, установите WARP:

```console
sudo rwm warp install --accept-tos
```

Флаг `--accept-tos` обязателен: он явно подтверждает принятие [условий Cloudflare](https://www.cloudflare.com/terms/). Во время операции менеджер:

1. создаёт локальную проверенную резервную копию;
2. устанавливает `iproute2`, `nftables` и `wireguard-tools` из Ubuntu;
3. получает и проверяет зафиксированный `wgcf`;
4. регистрирует аккаунт и создаёт профиль во временном закрытом каталоге;
5. записывает `/etc/wireguard/warp.conf` и credentials с правами `0600`;
6. запускает `wg-quick@warp.service`;
7. выполняет TLS-запрос Cloudflare через `SO_BINDTODEVICE=warp` и ожидает `warp=on` или `warp=plus`;
8. проверяет, что контейнер Node видит `/sys/class/net/warp`;
9. включает собственный таймер systemd для проверки состояния.

Если установка завершается ошибкой, менеджер останавливает созданные службы WARP и возвращает снимок конфигурации, `account.toml`, бинарного файла, license notice и файлов проверки состояния. Уже установленные пакеты Ubuntu не удаляются.

Если ошибка произошла после регистрации, менеджер пытается удалить только что созданный Cloudflare device. При недоступности API временный каталог с credentials не удаляется, его путь указывается в сообщении о неполном rollback. `scan`, новая установка, takeover и ротация обнаруживают такие каталоги и запрещают новую регистрацию до ручного recovery.

## WARP+

Лицензионный ключ не принимается параметром командной строки. Поддержаны только переменная окружения `WGCF_LICENSE_KEY` и скрытый интерактивный ввод:

```console
sudo rwm warp install --accept-tos --plus
```

`--plus` запрашивает ключ скрыто, если `WGCF_LICENSE_KEY` отсутствует. Если переменная уже задана, она используется и без `--plus`. При запуске через `sudo` переменную нужно разрешённым способом передать в окружение root; не добавляйте ключ в argv, историю shell или файл документации.

Ключ передаётся через очищенное окружение только процессу `wgcf update`; `register` и `generate` его не наследуют. Команды с регистрационными данными помечаются как чувствительные. Менеджер не записывает сам лицензионный ключ в `state.json`; файл `account.toml`, созданный `wgcf`, является секретом и хранится с правами `0600`.

## Принятие существующего WARP

Команда `scan` только обнаруживает конфигурацию, активный интерфейс и сервисы. Дополнительная проверка без изменений с учётом контракта текущей Node выполняется так:

```console
sudo rwm warp adopt
```

Она не переводит WARP под управление. Для takeover сначала изучите обычный или JSON-отчёт, затем выполните:

```console
sudo rwm warp adopt --takeover
```

Для неинтерактивного подтверждения доступен реальный параметр команды:

```console
sudo rwm warp adopt --takeover --yes
```

Takeover разрешён, только если найден обычный файл `/etc/wireguard/warp.conf`, его структура успешно разобрана и отсутствуют конфликты. Проверка требует:

- ровно по одной секции `Interface` и `Peer`;
- `Table = off` и отсутствие `DNS`;
- отсутствие командных хуков и неизвестных параметров;
- корректные WireGuard keys, адреса и endpoint;
- `MTU = 1280` и `PersistentKeepalive = 25`;
- IPv4 default-префикс `0.0.0.0/0` в `AllowedIPs`;
- отсутствие активного или включённого в автозапуск официального `warp-svc.service`;
- root-владельца и отсутствие group/other write у каталогов и найденных account-файлов.

После успешного takeover исходный legacy account-файл сохраняется как резервная копия и
показывается в списке legacy-файлов. Для уже управляемого WARP менеджер выводит
`Повторный takeover: не требуется`; наличие сохранённой копии не считается конфликтом.

Другие файлы `*.conf` в `/etc/wireguard` и известные устаревшие пути показываются в отчёте, но сами по себе не блокируют takeover. Менеджер не удаляет их. Если существует `/etc/cron.d/warp-native`, он безопасно отключается до изменения WARP runtime и после успешного takeover остаётся как `warp-native.disabled-by-remnawave-manager`; при ошибке исходный cron восстанавливается. Прочие чужие службы, задания cron и правила нужно проверить отдельно. Символическая ссылка вместо `warp.conf` запрещена.

Перед takeover создаётся резервная копия. Менеджер также запоминает изменяемые файлы, состояние `wg-quick@warp.service` и собственного health timer. При ошибке он возвращает файлы и исходное состояние служб, а уже переименованный узнаваемый legacy cron возвращает на прежнее место. Если какая-либо стадия самого rollback завершается ошибкой, команда перечисляет невосстановленные действия. Не применяйте `--takeover`, пока отчёт не изучен и неизвестные автоматизации WARP не отключены: произвольные чужие службы и задания менеджер намеренно не изменяет и не может проверить за их пределами.

Локальный проверяемый `wgcf` можно передать и при takeover:

```console
sudo rwm warp adopt --takeover --wgcf-file /root/wgcf_2.2.32_linux_amd64
```

## Состояние и управление

```console
sudo rwm warp status
sudo rwm warp start
sudo rwm warp stop
sudo rwm warp restart
```

`status` показывает фактическую активность сервиса, желаемое состояние, результат Cloudflare trace и возраст последнего WireGuard handshake. `stop` отключает автозапуск WireGuard и health timer до следующего `start`/`restart`; обе команды запуска включают unit обратно. Для stop и restart требуется подтверждение; его можно передать соответственно как `--yes`:

```console
sudo rwm warp stop --yes
sudo rwm warp restart --yes
```

Системный timer вызывает одноразовую проверку:

```console
sudo rwm warp watchdog
```

Обычно запускать её вручную не нужно. После трёх последовательных ошибок без свежего handshake watchdog может перезапустить WireGuard, но не чаще одного раза за 10 минут и не более трёх раз за час.

## Ротация аккаунта и профиля

```console
sudo rwm warp rotate --accept-tos
```

Для WARP+:

```console
sudo rwm warp rotate --accept-tos --plus
```

Ротация создаёт резервную копию и новые аккаунт и профиль во временном каталоге. До переключения запоминаются текущие `warp.conf`, `account.toml`, state, бинарный файл и точные `enabled`/`enabled-runtime` и active-состояния обоих units. Credentials прежнего device копируются в тот же закрытый staging и проверяются до регистрации нового device.

До локального commit любая ошибка возвращает прежние файлы и состояния units, после чего менеджер пытается отозвать только что зарегистрированный Cloudflare device. При недоступности API staging с credentials сохраняется, а rollback помечается как неполный.

Локальный commit происходит только после проверки нового профиля, восстановления исходных состояний units, удаления устаревшего управляемого `wgcf` и атомарного сохранения нового state. После commit менеджер отзывает прежний Cloudflare device и удаляет staging. Если этот финальный cleanup прерывается или Cloudflare API недоступен, новая рабочая конфигурация остаётся применённой и автоматический откат намеренно не выполняется: прежний device уже мог быть отозван. Закрытый `.rotate-*` каталог сохраняется для ручного recovery, а дальнейшая ротация блокируется до его проверки и удаления.

## Удаление

Остановить WARP временно следует командой `warp stop`. Полное удаление управляемых units и бинарного файла:

```console
sudo rwm warp uninstall
```

По умолчанию `warp.conf` и `account.toml` сохраняются. Для их удаления:

```console
sudo rwm warp uninstall --purge-credentials
```

Обе операции требуют подтверждения вводом `y`; для автоматизации доступен `--yes`. Перед удалением создаётся резервная копия. Дополнительно команда снимает оперативный snapshot изменяемых файлов и точных состояний units: если удаление завершается ошибкой, она возвращает файлы и исходное состояние служб. Неполный rollback перечисляется в ошибке и не маскируется успешностью архива. Файл, который после установки был изменён и больше не совпадает с записанным хешем, автоматически не удаляется.

Обычный `uninstall` сохраняет credentials и служебный `state.json`, поэтому `start`, `rotate` и повторный `warp install` будут отклонены: для временного отключения используйте `warp stop`. Вариант `uninstall --purge-credentials` удаляет также `state.json`, после чего чистая установка разрешена, если `warp scan` не находит прежний config/account или активный legacy cron. Takeover намеренно не удаляет исходный `/root/wgcf-account.toml`; перед новой регистрацией после purge его нужно отдельно проверить и безопасно архивировать. До полного удаления сохраните нужные credentials отдельно: обычный `backup restore` не возвращает supplemental WARP-файлы автоматически.

## Резервные копии и границы восстановления

Посмотреть и проверить локальные архивы можно командами:

```console
sudo rwm backup list
sudo rwm backup verify /var/backups/remnawave-manager/ИМЯ_BACKUP.tar.gz
```

Резервная копия Node включает управляемые файлы Compose, env, nginx и сайта. Каталоги `/etc/wireguard`, `/var/lib/remnawave-manager/warp`, зафиксированный `wgcf` и службы WARP systemd также попадают в архив как дополнительные материалы. В manifest они имеют `restore: false`: команда `rwm backup restore` не восстанавливает их автоматически.

Из этого следуют важные границы:

- `install` и `rotate` имеют собственный оперативный откат перечисленных файлов и компенсирующий отзыв нового Cloudflare device;
- обновление Node не изменяет WARP-файлы и при откате восстанавливает управляемую конфигурацию Node;
- `takeover` имеет оперативный rollback всех файлов, служб и legacy cron, которые изменяет менеджер;
- `uninstall` имеет собственный оперативный rollback изменяемых файлов и units, но обычный `backup restore` позднее не разворачивает WARP автоматически из supplemental-файлов архива;
- успешность архива и его контрольных сумм не означает, что учётные данные WARP можно вернуть командой `backup restore`.

Храните отдельную защищённую копию учётных данных WARP перед takeover, их удалением или ручными изменениями.

## Маршрутизация доменов через Panel API

Сначала убедитесь на соответствующей Node, что WARP работает:

```console
sudo rwm warp status
```

На сервере Panel примените маршрутизацию к существующему Config Profile:

```console
sudo rwm api warp-routing apply --base-url http://127.0.0.1:3000 --profile-uuid 00000000-0000-0000-0000-000000000000 --domain example.com --domain example.net
```

API-токен администратора читается из `RWM_API_TOKEN` или запрашивается скрыто. Он не принимается в argv. Команда добавляет:

- исходящее подключение с зарезервированным тегом `RWM_WARP`, протоколом `freedom`, стратегией `UseIPv4` и `sockopt.interface: warp`;
- первое правило маршрутизации со списком указанных доменов и `outboundTag: RWM_WARP`.

Если профиль содержит точную конфигурацию `warp-out`, которую создавал `remnawave-reverse-proxy` (`freedom`, `UseIP`, `sockopt.interface: warp`, `tcpFastOpen: true`), `apply` заменяет её новым outbound и одним правилом `RWM_WARP`, а не создаёт второй параллельный маршрут. Указанный в команде список доменов становится новым полным списком правила. Изменённая или неоднозначная структура `warp-out` не считается принадлежащей менеджеру: операция завершается до PATCH и требует ручной проверки профиля.

Перед PATCH полный JSON профиля сохраняется с правами `0600` в `/var/lib/remnawave-manager/api-backups/`. Затем профиль читается повторно: если его хеш изменился параллельно, PATCH отменяется.

Удаление разметки менеджера:

```console
sudo rwm api warp-routing remove --base-url http://127.0.0.1:3000 --profile-uuid 00000000-0000-0000-0000-000000000000
```

Тег `RWM_WARP` зарезервирован: `apply` отвергает исходящее подключение с этим тегом и другой структурой, а `remove` удаляет только исходящее подключение и правило с точной узнаваемой структурой менеджера. `remove` также умеет убрать точную legacy-конфигурацию `warp-out`. Объекты с зарезервированным тегом, но чужой структурой, автоматически не изменяются. Не используйте эти теги для ручной конфигурации.

API-команда не проверяет, что WARP активен на всех Node, использующих профиль, и не разворачивает WireGuard на них. Файл из `api-backups` не имеет отдельной автоматической CLI-команды восстановления. После изменения проверьте каждую Node через `rwm warp status` и фактический доступ к выбранным доменам.

## Лицензии и условия

Полный текст уведомления находится в [NOTICE](../NOTICE).
