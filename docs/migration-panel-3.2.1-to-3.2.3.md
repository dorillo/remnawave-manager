# Обновление Panel до 3.4.5

Менеджер проверяет и обновляет Panel до `3.4.5`, Subscription Page до `8.0.0` и PostgreSQL до `18.4` по digest из `compatibility.json`.

В Panel 3.4.0-3.4.1 добавлены штатные Prisma-миграции режимов привязки Host к Internal Squads и тегов сущностей. Новые параметры генерации short UUID имеют безопасные upstream defaults. В [3.4.5 относительно 3.4.4](https://github.com/remnawave/backend/compare/3.4.4...3.4.5) нет новых миграций, изменений Compose или обязательных ENV. Контракт API остаётся `@remnawave/backend-contract@3.4.15`. Добавленная `SERVICE_SNI_VERIFICATION` по умолчанию равна `true`; менеджер не перезаписывает существующее значение, в том числе `false`. Это SNI соединения Panel → Node, а не клиентский SNI Reality/XHTTP/CDN. Новая установка задаёт `true` явно. Существующий `.env` остаётся валидным, пользовательские `SHORT_UUID_*` сохраняются.

Миграции запускаются entrypoint Panel; вручную менять схему не нужно. До остановки сервисов менеджер скачивает и проверяет все целевые образы. Затем останавливает Panel и Subscription Page, создаёт согласованный backup базы и конфигурации и только после этого переключает версии. При ошибке после изменения файлов восстанавливаются dump, конфигурация и прежние образы. После запуска проверяются Panel, Subscription Page, обязательные API scopes и nginx.

В Compose меняются только прямые `image` выбранных сервисов; домены, токен Subscription Page, CDN и пользовательские настройки сохраняются. Для старой Panel выполняется миграция известных ENV-ключей в формат v3; nginx получает штатные исправления gzip и совместимости. Managed nginx/env/site-файлы защищены от параллельных изменений drift-проверкой и хешами. Отдельные серверы Node с XHTTP stream separation, Reality и WARP эта операция не затрагивает. После запуска менеджер возвращает исходный набор running/stopped-сервисов.

Сначала установите обновлённый менеджер из этой версии репозитория (`sudo ./install.sh install`). Затем на сервере Panel выполните:

```bash
sudo rwm adopt --path /opt/remnawave --role panel
sudo rwm diagnose
sudo rwm backup create --reason before-panel-3.4.5
sudo rwm update --yes
```

Если исходный образ не доказан по digest или конфигурация изменилась после adoption, операция останавливается до любых изменений. Не используйте `--accept-unknown-source`, если источник нельзя независимо проверить.

Если диагностика обнаружила небезопасные права приватных managed-файлов, выполните `sudo rwm diagnose --repair-permissions`, затем повторите диагностику. Ручной backup выше — дополнительная копия: `update` создаёт собственный согласованный backup после остановки приложений.

После успешного обновления Panel можно обновлять менеджер и Node до 3.4.2 на каждом сервере ноды по [инструкции](update-node-3.0.0-to-3.1.1.md). Переустановка Node не требуется. Обновление приложений само по себе не заменяет сайты-заглушки — для этого используется [управление сайтами](node-sites.md).

## Объём проверки 6 октября 2026 года

Для Manager 0.1.26 сверены исходники релизов Panel 3.4.5 и Node 3.4.2, Compose, ENV-схемы, миграции, Node `SECRET_KEY`, команды `cli`/`rw-core`, версия встроенного Xray и multiarch digest в Docker Hub/GHCR (`linux/amd64`, `linux/arm64`). Subscription Page остаётся на последнем теге `8.0.0` с прежним digest. Сгенерированные ENV проверены официальными Zod-схемами; запросы регистрации, входа, токенов, профилей, Node, Host, Internal Squads и WARP — пакетом `@remnawave/backend-contract@3.4.15`. Для Reality и XHTTP проверяется сохранение вложенных полей API, а для обновления Node — CDN/nginx, ENV, сертификатов, WARP и сайтов. Отдельно проверены повторное обновление текущих версий и сохранение пользовательских SNI/short UUID.

В полном локальном pytest-прогоне на Windows: 817 passed, 35 skipped, 7 failed; те же семь падений воспроизведены на исходном HEAD до изменений (POSIX-права, символьные ссылки, Unix-пути/переводы строк). Новых падений нет. Docker и Linux runtime в этой среде отсутствуют: запуск контейнеров на Ubuntu 24.04, реальное восстановление базы и VPN-трафик через CDN/WARP в этот аудит не входят. При обновлении сервера менеджер выполняет собственные preflight, health checks и транзакционный откат; локальная проверка не заменяет их.
